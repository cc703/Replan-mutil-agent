# P1 契约评审提案

状态：PROPOSED；G4 PENDING。推荐不等于批准，也不冻结契约。原文以 `docs/source/codex_spec_v1.1.original.md`（下称 S）及 `docs/source/design_v2.original.md`（下称 D）为准；数字为行号。

## 人员资源

依据 D:211、214、217、226、451、758；S:293–306、325–338、376–380：规格缺人员字段但保留 V7。提议以下伪定义（不是代码或已定契约）：

| 对象/字段 | 类型及默认 | 约束与旧 JSON |
|---|---|---|
| Person.id | 字符串，必填 | 非空、实例内唯一；新实体必须带 id |
| Person.skills | 字符串集合，默认空 | 元素非空；空为无技能 |
| Person.blocked | 区间集合，默认空 | 整数槽半开 [start,end)，start < end，视野内；空为无阻塞 |
| Task.required_skills | 字符串集合，默认空 | 元素非空；旧数据缺省空 |
| Task.requires_person | 布尔，默认 false | 旧数据缺省 false |
| Assignment.person_id | 可空字符串，默认 None | 非空时必须引用已知人员；旧数据缺省 None |
| Instance.persons | Person 集合，默认空 | ID 唯一；旧数据缺省空 |

技能可选单字符串（贴近 D 的单数）或集合；推荐集合，表示全部要求均须具备。人员需求可仅用技能非空推导，或增加显式开关；推荐 `requires_person OR required_skills 非空`，从而支持无技能但需要人员。非必需任务可不分配；一旦分配，仍检查引用、技能、人员互斥及日历。旧 JSON 缺这些字段时不引入人员约束，既有无人员行为不变；显式新增人员数据才启用相应约束。Person.id 不是旧模型的新增字段，不能缺省。阻塞窗口与设备的非开放窗口方向一致；开放窗口替代方案则需定义视野及空集含义，空集会产生反直觉的全不可用。推荐阻塞窗口。人员是否占设备准备时间、DONE 历史占用、V8/V11 是否冻结 person 均待裁决，以下例子仅指任务执行区间。

V7 建议覆盖缺分配、未知人员、技能不足、同人重叠、人员阻塞冲突；不改 V1–V11 编号，不把这些情况静默通过。选项为 detail 表达原因，或新增结构化 subcode；推荐 detail 作为当前提案，subcode 修改 Violation 契约须 G4。数据形状或引用错误先报告，后续依赖检查 N/A；不可因 N/A 判通过。

### 分层等价类与例子

以下顺序覆盖有效组合及无效数据；后续行以前层成立为条件，不是互斥的唯一错误清单。所有区间均半开；人员可选分配也经过相同检查。P1 拟测以下各行，具体实现须 G4 后另立工作包。

| 层 | 条件及最小例子 | 结果 / 不适用原因 |
|---|---|---|
| 需求与集合 | persons 空，需人员（开关 true，或技能 {A}） | 失败 V7；分配、技能、重叠、日历无可用对象，N/A |
| 需求与集合 | persons 非空，需人员，person_id None | 失败 V7；后续 N/A |
| 需求与集合 | persons 空或非空，非必需，person_id None | 人员部分通过；技能、重叠、日历 N/A，因为无分配 |
| 引用 | 任何任务 person_id=X，X 未知（包括 persons 空） | 失败 V7；技能、重叠、日历 N/A |
| 技能 | 需 {A}，已知人员技能 {} | 失败 V7；引用有效后仍可检查冲突 |
| 技能 | 需 {A}，人员技能 {A}；或空技能要求且已知人员 | 技能通过；空要求为平凡通过，后续仍检查 |
| 互斥 | 同人 [1,2)、[2,3) | 通过；相接不重叠 |
| 互斥 | 同人 [1,3)、[2,4) | 失败 V7；不同人员同时间不触发人员互斥 |
| 日历 | [1,3)，阻塞空；或阻塞 [3,4) | 通过，空无阻塞且相接不交叉 |
| 日历 | [1,4)，阻塞 [2,3)；或 [1,3) 与 [2,4) | 失败 V7，分别为跨越与部分重叠 |
| 数据合法性 | 重复人员 ID、反向或零长度阻塞、空技能名 | 输入语义失败；不能将后续 N/A 当通过，错误归属待 G4 |

P1 不测事件实现、求解器建模、实际缺席传播；PERSON_ABSENT 影响人员可用性、受影响集合和重规划，生成器需生成一致人员与日历，仅登记影响，不设计事件（D:357、584）。

## 其他缺口：选项与推荐

1. **V2/V9**（D:448、453–455、753、760；S:290、306、314–323）：原文单设备互斥与累计容量并存。选项统一容量码或按容量分流；推荐 capacity=1 用 V2，>1 用 V9，同一违规只报一个码。任务及其准备占用依任务 demand，阻塞占满容量；demand>capacity 必失败。影响独立校验和求解；准备的容量语义须 G4。无裁决则不能实现一致错误归属。
2. **时间**（S:278–285；D:224–228）：选项拒绝非整槽，或保守舍入；推荐 release、duration 向上，deadline 向下，阻塞起点向下终点向上；拒绝 naive datetime，保留带时区转换。舍入致不可行应明确返回不可行，不能放宽约束。影响导入与边界；不裁决阻塞转换实现。
3. **solve_initial**（S:423–446）：None 不能区分超时与不可行。选项结构化结果、None 加异常、复用 ReplanResult.status；推荐结构化结果，区分最优、可行、不可行、超时未知、模型非法，并在有计划时携带计划。影响调用方与测试；不裁决阻塞接口实现。
4. **RUNNING 工期/V10 — OPEN-DATA-SOURCE**（S:293–306、368–371；D:453、761）：new_end 仅在事件，Instance 无持久来源。选项新增 Instance/Task 字段、Plan 元数据、调用方传参；分别影响输入契约、计划版本一致性、调用链与可重放性。暂推荐调用方显式传入，推荐≠批准。候选 V10：RUNNING 对当前预计 end 校验，未开始任务按 duration 校验；另可统一 duration，但无法表达超时。无来源则不能可靠校验或重放，不得假定来源已定。
5. **冻结 end/V11 — OPEN-DATA-SOURCE**（D:453、759–762）：V8 固定设备与开始，V11 要求 Free 外未变；超时导致 end 变化的依据及是否视为违规不明。选项授权事件解释的 end 变化，或严格报 V11；暂推荐有证据的变化例外，推荐≠批准。需可追溯来源；无裁决阻塞相关校验。
6. **NEGOTIABLE — OPEN-DATA-SOURCE**（S:300；D:441、462、555、756）：默认按硬并显式记录放宽，或默认入目标。前者需原截止、授权后截止、授权人/时间/作用域及版本；后者需迟延权重及是否获得授权的可审计状态。推荐前者，推荐≠批准；现有字段无放宽凭证，V5 无法识别授权。两路线影响目标与校验；未裁决阻塞此语义。

## G3 R1–R5 返工：供选择的细化条款（均 PROPOSED）

### 人员占用边界（裁决清单第 2 项的三个独立选择）

- **准备时间**：A 人员占用执行及设备准备区间；B 仅占执行区间。推荐 B：现有技能需求明确对应任务，避免未确认的人力准备假设；A 更保守但可能排除可行计划。选择影响人员互斥、日历及求解；未裁决阻塞这些边界实现。设备准备的容量规则仍为另一项提案。
- **DONE 历史**：A 仅校验当前计划视野内的历史执行占用，超出视野的历史不作为当前资源占用，但仍保存审计；B 对完整历史与当前计划一起校验。推荐 A，避免历史和当前资源约束混淆；实际视野与历史边界须明确定义。B 有助全历史审计但需要完整可靠的人员记录。未裁决阻塞 DONE 人员冲突校验。
- **冻结 person**：A 已分配人员的冻结任务保持 person 不变；B 允许变更人员并记录原因。推荐 A，保持已承诺资源稳定；B 提高应对缺席的灵活性。V8 原文仅设备和开始（D:759），若将 person 纳入 V8 属于修改；另一方式保持 V8 原义，由 V11 的 Free 外全字段规则处理 person，推荐后者但具体例外仍须裁决。V11 的 end 超时问题是独立数据来源议题，不以本选择解决。未裁决阻塞重规划冻结校验。

### 时间转换接口与边界（裁决清单第 4 项）

S:280–285 的 `to_slot(dt)` 没有语义方向；S:297 的 duration 已是整数槽而非 datetime。A 保留通用 `to_slot(dt)`，在外部输入适配层按字段使用明确的方向转换，外部 duration 先按时长/槽长向上取整，再构造整数槽 Task；B 提议扩展方向参数或分别定义 release、deadline、阻塞和 duration 的专用转换接口。推荐 A，兼容原签名；推荐通用 to_slot 对非整槽拒绝，因为其签名无字段语义，无法安全选择舍入方向；字段保守舍入由外部适配层显式执行。替代为给通用接口增加方向参数或定义专用接口；该行为仍须 G4 裁决，不能假定截断。B 的调用意图更直接但改变公共 API。内部已经是整数槽的输入不重复转换。两者均须在 G4 确定后实施。

示例：t0 08:00、5 分钟槽，release 08:01→1，deadline 08:09→1，duration 6 分钟→2 槽，阻塞 [08:01,08:09)→[0,2)；恰好对齐 08:05→1。naive datetime、非正 duration、反向窗口为输入非法；舍入后 release=1、deadline=1、duration=2 形成无可行窗口，推荐作为确定的预检查不可行，与非法输入区分；也可交求解器报告不可行。多任务竞争导致不可行则为求解不可行；超时未知不能归为不可行。无裁决阻塞导入转换及状态映射。

### RUNNING/V10 判断候选（裁决清单第 6 项，OPEN-DATA-SOURCE）

令 s 为可靠实际开始槽，d 为原计划 duration，e 为计划中的当前结束槽，c 为最新有效预计结束（例如事件 new_end，但须有明确来源与顺序）。候选 A（推荐）：未开始任务 e−s=d；RUNNING 要求 e=c 且 c>s，不再要求 e−s=d 或 e≥s+d；实际开始如何记录和校验也需裁决。候选 B：RUNNING 要求 e≥s+d 且 e≥c，保留原 duration 下界；候选 C：所有状态 e−s=d。A 能表示超时和提前结束预测，B 排除提前结束，C 无法表达超时。

例如 s=10、d=4、c=16，A 要求 e=16，B 可接受 e≥16，C 要求 e=14；c=12 时 A 可接受 e=12、B 拒绝 e=12、C 仍要求 14。提前**预测**不等于已完成，实际提前完成及状态转移另须定义。缺 c 时选项是明确失败，或报告未验证且不得视为校验通过；推荐后者保持数据缺失与违规区分，并阻止正式展示/提交。两者都不能静默通过。调用方传入只是来源路线推荐：类型、具体 API、事件排序、持久化及重放策略均未裁决；其他条款不依赖此路线成立。

### 可复制的文档示例：输入与预期

以下 JSON 只是契约提案的示意，非 fixture 或实现；都含 S 中最小必要字段。示例仅说明人员层结果，完整计划还须通过其他校验。旧数据：

